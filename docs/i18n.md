# Localization

CakeFlow UI copy lives in next-intl message files, never in components.

## Locales

- `uk` — default, initial market
- `en`

Routing is in `src/i18n/routing.ts`. `localeDetection` is off so a first visit
is Ukrainian even when the browser prefers English. After a user switches,
the URL prefix (`/uk/...`, `/en/...`) is the source of truth.

## Adding copy for a feature

1. Add a namespace to both `src/i18n/messages/uk.json` and `en.json`.
   Keep the key trees identical.
2. In a Server Component, `const t = await getTranslations("YourNamespace")`.
3. In a Client Component, `const t = useTranslations("YourNamespace")`.
4. Pass already-translated strings into shared primitives (`Button`, `SpecRow`,
   `PageHeader`). Primitives never own copy.

Server actions return message keys (for example `errors.nameRequired`), not
sentences. The form component looks the key up with `t(...)`.

## Dates and times

Use `formatDateTime` from `src/i18n/format.ts` on the server, or
`useFormatter().dateTime(...)` in client code. Do not call `toLocaleString`
with a hardcoded locale.

The request time zone is `Europe/Kyiv`. Display format still follows the
active UI locale (`uk` vs `en`).

## What not to translate

User-entered bakery, catalog and order content is stored and shown as typed.
Translate labels around that content, not the content itself.

## Language switcher

`LocaleSwitcher` (`src/i18n/locale-switcher.tsx`) is the UI for changing
locale. Place it in chrome (shell, auth, landing), not inside feature forms.
